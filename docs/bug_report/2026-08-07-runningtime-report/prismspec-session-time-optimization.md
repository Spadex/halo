## 三、优化清单（按可省时间排序）

### 优化 1：评审 fail 即分诊，「需人裁定」的分歧不重派评审 ⭐ 可省 30min+

**规则**：任一轮独立评审判 fail 后，主代理先把 fail 项分为两类再决定下一步：

- **实现缺陷**（代码/测试/证据可修）→ 修复后重派评审，正常。
- **spec 层分歧**（AC 措辞、锚点形态、边界未定义等，修复方案会改动 spec 语义）→ **立即停下问用户裁定**，禁止「先修一版再派一轮评审试试」。

**判别信号**：如果对 fail 项的修复需要改 `spec.md` 的 AC/不变量正文，或评审者两轮指出的是同一条目，即属 spec 层分歧。

**本次教训**：T3 第 1 轮 fail 已暴露 AC-4 锚点问题，第 2、3 轮（合计 40min）只是撞了同一堵墙，最终仍然是留给用户裁定。

### 优化 2：评审规格分档，简单任务不配深度评审 ⭐ 可省 10–20min

**现状**：T2 一轮 6.3 min 即 pass；T3 每轮 11→15→25 min 递增（评审者自建沙箱、复跑变异、自跑 git 核史实）。

**规则**：派发评审时按任务复杂度给出**范围提示**（不是预设结论）：

- 纯代码/测试改动、无史实断言 → 标准评审：AC 覆盖 + 断言质量 + diff 逐行，不要求评审者重建变异沙箱。
- 涉及史实核对、知识库改写、元测试 → 深度评审：允许沙箱复跑与 git 溯源。

注意边界：这是限定**核查手段的深度**，不是限定评审可报什么问题——「不要报 X / 最多算 minor」类措辞仍然禁止（见 `~/.claude/CLAUDE.md` 常驻授权的边界条款）。

### 优化 3：限流后先短等重试，不转入长推理自审

**现状**：限流后主代理立刻转自审，单次推理 10.9 min，之后限流恢复还是重派了评审（自审成果部分重复）。

**规则**：分类器限流时，先做 1–2 个**小粒度**只读核查（单条命令能出结果的），间隔几分钟重试派发；不要启动整段自审推理链。限流通常是分钟级的。

### 优化 4：上下文超 250k 时收口分段

**规则**：PrismSpec 全流程会话中，进入 `/review` 或 `/verify` 阶段前如上下文已超 ~250k，先把阶段结论落盘到工件（`review.md` / `verify.md` 草稿），然后 `/clear` 后凭工件续跑。PrismSpec 的阶段工件本来就是为断点续跑设计的（guide.sh 从 artifacts 恢复状态）。

**收益**：后半程 55 条消息不必每条背 378k 上下文；也降低超长上下文下的注意力稀释风险。

### 优化 5：effort 分层（已执行）

xhigh 已改为 high 并存为默认。评审子代理如需更高强度，可在派发时单独指定，不必让主代理全程 xhigh。

## 四、不建议改的

- **独立子代理评审本身**：本次评审质量实打实（史实逐条独立 git 复核、变异沙箱证伪），T3 的 fail 都是真问题。要压的是轮次与分档，不是取消独立评审。
- **Bash/测试环节**：109 次共 16.5 min，无优化空间。
