## 总账：4 个小时花在了哪里

```
turn 3 活动窗约 224 min（turn_duration 记 246.9 min，含约 23 min 计时前置）
├─ 评审子代理串行阻塞    93.5 min   ~42%   ← 最大单项
├─ 主代理 LLM 往返       ~80 min    ~36%   = 197 次往返 × 平均 24.9 s
├─ Bash 实际执行         ~21 min     ~9%
└─ 其他空窗与杂项        ~30 min    ~13%
```

两个乘数决定了主代理那 80 分钟：**往返多少次**（197 次）和**每次多贵**（24.9 s，且随上下文膨胀
从 13.6 s 一路涨到 32.3 s）。评审那 93.5 分钟则是纯粹的干等——主代理在每个评审窗口内零活动。

下面 5 件事按预估省时降序排列，全部落地后该 turn 预计压到**约 2 小时**。方案 1 与方案 3 作用于
同一块时间（评审阻塞），收益有重叠，不能简单相加。

## 1. 评审点批量化：6 个评审点压到 2–3 个（省 30–50 min）

### 问题

9 个任务派了 6 次独立评审，每次 13–30 分钟，主代理全程干等，合计阻塞 93.5 分钟——比主代理自己
写代码的时间还多。其中 RED-1、T1、T2 是单任务单评审；只有 RED-2/3、T3/T4、RED-4/T5 做了两任务
合并。

### 为什么慢

每次评审都有一笔**与被评审任务数无关的固定开销**：

- 约 22% 的时间花在上下文重建（找 reviewer 契约、列制品、读 spec/plan 定位任务段）；
- 常规检查（git 状态、跑全套测试、比对评审包与工作树 diff）也大部分是固定的——评审 1 个任务
  和评审 3 个任务，测试都是全量跑一遍。

6 个评审点就要付 6 笔固定开销。评审的真正价值——独立验证（约占 42%）——才是随任务量线性增长的
部分。

### 解决方法

- **plan 阶段就把评审点画进任务清单**：RED 批（RED-1~4）一个评审点，T 批一到两个评审点，而不是
  实施时临场决定。批边界判据只有一条：**改动面重叠、或后置任务建立在前置任务代码上的任务，必须
  同批评审**——保证任何缺陷都在下一批开工前被拦住。
- 流程上没有障碍：SKILL.md 只要求「一次评审用一个评审者」，不限制一个评审点覆盖几个任务；本期
  三次合并评审已顺利通过全部门禁。
- 同批任务共用一份评审包与一次全量回归，评审者一次上下文重建覆盖 2–4 个任务。

### 收益与风险

评审总阻塞预计从 93.5 min 降到 45–60 min。风险是批内后置任务若依赖前置任务的缺陷代码，发现时点
比逐任务评审晚、返工面更大——但本期 T3/T4 合并评审照样抓出了 Critical（SQLite `json_each` 的
OFFSET 缺陷），说明合并不损失查出率；且上面的批边界判据已把返工面兜在批内。

## 2. 任务实施下放子 agent，应分尽分（省 35–40 min 起，RED 并行可再压墙钟）

### 问题

8 个任务塞在一个会话里，上下文单调膨胀：会话前期平均 23 万 token 时单轮 13.6 s，后期 47 万时
32.3 s——**同样一次往返，后期比前期贵一倍还多**。

### 为什么慢

实测延迟对上下文规模的斜率约为 **70 s/百万 token**（分桶：231k→13.6s、284k→19.5s、359k→26.3s、
471k→32.3s）。主会话的上下文只增不减：每完成一个任务，它的全部实施细节（命令、测试输出、
返工过程）都永久留在历史里，后面每个任务的每次往返都在为此付费。8 个任务的会话里，最后一个
任务的每轮成本是第一个任务的两倍多。

### 解决方法：子 agent 隔离执行

把任务实施下放到独立子 agent，主会话退为**编排者**——只做派发、收结果摘要、串行收口、评审调度。
收益来自两个机制：

1. 子 agent 从小上下文起步（几万 token，约 10–14 s/轮，对比主会话后期的 25–32 s）；
2. 主会话只积累每个任务的**摘要**而非实施全过程，后续所有任务的每轮成本不再被前面任务的细节
   推高——这是比「省下子 agent 自己那部分」更持久的收益。

**范围与原则：RED 与 T 任务都适用，应分尽分**——只要切分**无伤害**（不丢关键现场知识、不产生
共享文件写冲突）且**有明显时间收益**（该任务留在主会话执行会为后续任务垫高上下文），就应该切。
RED 任务（只增测试文件、互不重叠）还可进一步并行派发，墙钟压到最慢的那一个；T 任务（生产代码、
有依赖链）默认串行子 agent。具体切分粒度与判据**由 halo 团队定夺**（建议进 SKILL.md，已随
`docs/halo-issues/2026-08-07-model-set-search-implement-findings.md` 一并提报），本文只给原则
与实测依据。

必须处理好的三个点：

- **共享写目标收口**：plan.md 复选框与 `.halo/sdd/` 是共享的，`task-complete.sh` 会写 plan.md。
  子 agent 只负责实施 + 写自己任务目录下的证据；收口一律收回主代理串行执行（配合方案 5 的
  合并命令，几个任务的收口也只是几次往返）。
- **现场知识靠制品传递**：子 agent 拿不到主会话的记忆。前序任务的发现（fixture 搭法、边界坑）
  本就要求写进 `report.md`，派发后续子 agent 时把相关 report 喂进去，不靠会话记忆。
- **每个子 agent 有固定成本**（注入 brief/spec 摘录、读回结果），对整任务级的切分是小钱；
  切得比任务还细就会得不偿失——这也是「应分尽分」里「有明显收益」这半句的含义。

**兜底形态**：暂不改派发方式时，退而求其次用**分会话**——RED 批一个会话、T 批一个会话，
收益同源略小。它是安全的：任务进度完全持久化在磁盘上（plan.md 复选框 + `.halo/sdd/` 制品），
`task-next.sh` 就是一条对 plan.md 的 grep，新会话 `/implement` 无损接续；RED 批的实测结论
写在各任务 `report.md` / `red-output.txt` 里，T 批会话按需读取。

### 收益与风险

串行子 agent 的收益不低于分会话的 35–40 min（平均上下文 36 万 → 约 20 万，按实测斜率折算），
且主会话瘦身让方案 1/3 的评审调度也更便宜；RED 批并行再额外压缩墙钟。风险集中在两点，均有
明确解法：共享文件写冲突（收口收回主代理）与知识断层（制品传递）。

## 3. 低耦合批的评审改 background 派发（省 25–30 min，与方案 1 部分重叠）

### 问题

5 次评审全部同步等待：派出评审子代理后，主代理在 13–24 分钟的窗口里什么都不做。

### 为什么慢

这是**自我强加的串行**。流程文档的真实约束只有因果一条——「Critical/Important 修完才能对该任务
执行 task-complete」——从头到尾没有任何一处要求同步等待评审结果。同步等待是执行习惯，不是规则。

### 解决方法

- **对只新增测试文件、不碰生产代码的 RED 批**：评审派发后立刻推进下一任务，评审通知回来再处理
  发现项。硬前提写死在执行约定里：*评审结论回来之前，不得对被评审的任务执行 task-complete*——
  因果约束原样保留，只去掉干等。
- **T 批（生产代码）默认不并行**：T 批评审可能返工生产代码（本期 T3/T4 的 Critical 触发了 9 次
  往返的修复），若此时已在其上叠新代码，返工面不可控。耦合紧就老实等。
- 与方案 1 组合的算法：先批量化（评审点变少），剩下的评审点里再对 RED 批用 background——两者
  作用于同一块 93.5 min，组合后评审阻塞预计压到 30–45 min，不能按各自省时相加。

### 收益与风险

单独实施省 25–30 min。风险中等：需要逐批判断「下一个任务是否建立在被评审代码上」，判断错了
返工面变大——所以只对 RED 批开放，判据简单（是否只动测试文件），几乎不会判错。

## 4. 评审派发提示写死制品全路径（省 15–18 min）

### 问题

每个评审子代理开局都要花 5–6 轮「找东西」：找 reviewer 契约在哪、任务制品在哪、spec/plan 在哪。
6 次评审重复 6 遍，合计约 18 分钟花在找路径上。

### 为什么慢

评审者的输入契约文档只把 `brief.md` 写成全路径，其余制品（report、评审包、TDD 证据）只给文件名
甚至只给名词——于是每个评审子代理都得自己 `ls`/`grep` 一轮把路径拼出来。而这些路径对每个任务
**完全相同**，是收敛的固定模式，本不该每次现场发现。

### 解决方法

派发提示模板直接写死（每次派发只需替换 `<spec-id>` 与任务号）：

```
评审契约：prismspec/agents/task-reviewer.md
任务制品：.halo/sdd/<spec-id>/<task-id>/{brief.md, report.md, review-package.md, tdd-evidence.json}
事实源：halo/specs/<spec-id>/{spec.md, plan.md}
```

这条只削「找路径」的纯开销，不改变评审要做什么——独立验证（约 42%）与防篡改校验一分不减。
顺带应向 halo 上报把 `task-reviewer.md` 的 Inputs 段补全（已列入
`docs/halo-issues/2026-08-07-model-set-search-implement-findings.md`），根治而不是每个项目各自打补丁。

### 收益与风险

每次评审省约 3 min × 6 次 ≈ 18 min（批量化后按剩余评审点折算）。零风险。

## 5. 压往返数：收口仪式合并单命令 + 独立调用一轮多发（省 15–25 min）

### 问题

主代理 197 次往返里，**193 次只携带 1 个工具调用**。最典型的浪费在任务收口：每个任务都要走
「写 TDD 证据 → 写 report → 生成评审包 → 归档评审记录 → 复跑 lint → 标记完成」六步，每步单发
一次 Bash——9 个任务约 45–54 次往返，全部烧在一个无分支的固定序列上。

### 为什么慢

每次往返的固定成本是平均 24.9 s（大头是重新处理几十万 token 的上下文，见方案 2），而收口每一步
的 Bash 本身只跑零点几秒。**往返次数是被序列长度硬撑起来的，不是被工作量撑起来的。** 这套序列
无分支、前一步成功后一步必执行、各步幂等；流程文档只规定了顺序与前置条件，从未要求分步执行。

### 解决方法

- **收口合并**：在项目 CLAUDE.md 加一条执行约定——*任务收口的固定步骤用 `&&` 串成单条 Bash
  提交，不拆开*。中间失败时整条重跑即可（幂等保证无害），各步自带的退出码打印足以定位失败点。
  每任务 6 次往返 → 1 次。
- **独立调用并行**：读文件、查状态、跑互不依赖的检查时，一轮里并行发多个工具调用，而不是
  一问一答串行。这是同一个杠杆的一般形式：能并行的调用绝不排队过上下文收费站。

### 收益与风险

收口合并约省 30–45 次往返 ≈ 12–15 min；读取/检查类并行再省若干。零风险——被合并的每一步
原本就要执行，只是不再各付一次 24.9 s 的往返税。

**门禁左移（省时约 10 min，但防的是最恶性的单点事故）**：本期 RED-1 收口被门禁拦住，定位根因花
了约 16 次往返——plan 任务正文的**散文**里出现了 `AC-N` 字面，被内核（`_lib.sh:215` 对整段正文
`grep -oE 'AC-[0-9]+'`）抓成必须提供红绿证据的覆盖声明。两步解决：① 立即生效的撰写纪律——plan
任务散文不写 `AC-N` 字面；② 已向 halo 提报在 `task-next.sh` 补逐任务 `ac_refs` 查询入口，落地后
plan 定稿时一条命令即可预检每个任务将被门禁认定的 AC 集合，把收口期搏斗左移成 plan 期的一次比对。

## 天花板：如果要动 spec/plan，三个明显受益的刀口

以上五件事解决的是「同样的流程跑得更快」，合计把 4 小时压到约 2 小时。剩下的 2 小时是流程重量
本身——9 个任务 × 每任务仪式 × 评审点数量，这些在 implement 期已无法改变，因为它们在 plan 定稿
时就被决定了。要再往下压，刀要落在 spec/plan 阶段。下面三刀都有实测依据，且都不碰质量护栏
（评审深度、变异自证、AC 设计一分不动）。

### 刀口一：任务按「可独立评审的行为增量」切，不按步骤切（估省 40–60 min）

每个任务是一笔固定仪式成本：约 6 次收口往返 + brief/report 读写 + 一次门禁风险敞口，合计约
10–15 min/任务——**与任务大小无关，只与任务个数有关**。本期 9 个任务，同样的交付物切成 4 个
（RED 合并为 1–2 个 + 迁移/索引 + 接口实现 + 回归护栏）就能省约 5 笔固定成本，评审点数也随之
自然下降。

合并不损失质量粒度：TDD 红绿证据本就按 AC 记录（`tdd-evidence.json` 的 `ac_ids`），四个 RED
任务合成一个，每个 AC 的红灯证据一条不少。任务上限的判据只有一条：**大到「一次评审仍能独立
验证它」为止**——超过这个尺寸，评审质量开始下降，就切开。

### 刀口二：plan 定稿时画好「执行拓扑」（不直接省时，但解锁方案 1 和方案 2）

批次怎么分、哪些任务可以子 agent 化/并行、评审点设在哪里——这些决定在本期是 implement 期
临场做的，做得保守（6 个评审点、零并行）。它们本该是 plan 的输出：任务间的依赖关系、改动面
重叠度，恰恰是 plan 阶段看得最清楚的时候。

做法：plan 模板加一节「执行拓扑」，定稿时写明批次划分、每批的评审点、可并行的任务集合。
implement 期照着执行，零决策成本。执行期的两大提速（评审批量化、子 agent 切分）都依赖这张图
先画好——机制细节已提报 halo 定夺。

### 刀口三：spec/plan 分层——执行层与背景层分离（估省 10–20 min + 持续压低上下文）

本期 spec.md 5.1 万字符 + plan.md 6.6 万字符，合计 11.7 万字符进上下文，且 plan.md 被完整读了
3 次。但 implement 与评审每轮真正需要的只是**执行层**：AC 表、任务卡、接口契约、门禁要求；
调研过程、备选方案对比、决策记录这些**背景层**内容，实施期几乎不会翻，却每次都跟着整个文件
进上下文。

做法：spec/plan 正文只保留执行层，背景层移到同目录附属文件（如 `research.md`、`decisions.md`），
正文按需引用。内容一字不减、事实源不变——只是分层存放，让 implement 期装进上下文的是薄的那层。
这与「不精简 spec/plan」的原则不冲突：砍内容伤质量，分层不伤。

### 这三刀之外的，依旧不做

削减全套回归频次、削减变异/鉴别力测试、削减评审的独立验证深度、删减 spec/plan 的实质内容——
这些表面省时、实际伤质量。本期评审抓出的 Critical 与变异自证拦下的弱断言，都是这些开销在产生
回报的直接证据。
